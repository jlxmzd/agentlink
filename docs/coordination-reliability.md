# 协作可靠性改进规格

状态：2026-11-04 已确认需求；除 T-20261104-01 正在实现外，下列内容为待实施规格，不表示已发布。

## 顺序与边界

先验收 T-20261104-01 的 AI 审查启动确认、自动重试和停滞提示，再实施接管与真实状态修正，最后加入执行心跳、问题闭环及可靠唤醒。实现同一状态机的任务串行领取路径锁。开发目录验收完成后另行同步公开仓库。

## 1. 投递与执行状态

- 明确区分 transport sent（桥接接受投递）、received（执行方显式确认）、running（执行方确认开始）、completed（交付持久化）。不能把 RPC accepted 或宿主 running 当作任务启动证明。
- 保留任务业务状态，执行阶段单独记录；完成执行不代表验收通过。
- 心跳携带任务 ID、执行代次、执行者和租约凭据；只延长当前执行租约。旧代次、错误身份或已终结任务不得更新。
- 记录 lastHeartbeatAt、leaseExpiresAt。超时显示疑似停滞并通知，不能自动宣告失败、成功或启动第二个执行者。旧宿主无心跳时标为未知。

## 2. AI 二次验收恢复

- 本项由 T-20261104-01 实现：started 回执、持久化有界退避、常规 pump 恢复、停滞提示。
- 重试同一投递使用稳定 requestId；发送租约防并发。若桥接不保证去重，结果不确定时不得盲目重投，应通知人工处理。
- 已启动审查不自动再派发；超时不是通过。旧 RPC 回包不能覆盖启动确认、终态或新代次。

## 3. 总控接管验收

- 仅当前项目总控或有明确权限的用户可显式接管，要求填写理由。
- 锁内原子更新审查负责人和审查代次，撤销旧审查 token 与发送租约；记录原负责人、新负责人、原因、时间、事件编号。
- 接管保留原程序验收、AI 回执和历史，不自动接受任务；新负责人仍须给出明确结论。
- 接管后的旧确认、心跳、验收结论及迟到 RPC 一律不可改变当前状态。

## 4. 返工问题逐项闭环

- 驳回形成带稳定 issueId 的问题列表，保留严重性、内容、提出代次和解决状态。
- 交付逐项回应：修复说明与证据，或未解决原因。响应覆盖每个未关闭问题，不能靠概述跳过。
- 执行方只能标为待复核；审查方确认关闭或重新打开。缺少必需回应时程序验收明确列出缺项。
- 旧版自由文本驳回兼容为一项历史问题；不得丢失原文或在迁移中伪造已解决状态。

## 5. 唤醒完整性与幂等

- 唤醒携带任务 ID、事件编号、当前状态、交付/审查代次、完整回执和明确下一步命令；凭据必须脱敏。
- 超过宿主消息限制时提供可校验的持久化回执引用及读取命令，明确截断，不能把摘要当完整回执。
- 去重键包括项目、任务、接收方、事件编号；持久化待投递与已投递状态，失败重试不得误记已送达。
- 重启后继续未完成投递；接收方可用事件编号识别重复消息，避免重复执行。

## 6. 接手和等待语义

- 总控或发起方接手执行时转交负责人并进入可执行状态，记录 takeover 事件，不标 cancelled。只有明确取消操作才取消。
- 转交原子撤销旧执行/审查授权，保留关联回执和归属历史；已有文件锁不能在转交窗口被错误释放。
- wait 超时保留真实 state，另返回 timedOut=true、等待时长及当前阶段；不以 state=waiting 覆盖事实。
- wait 覆盖 ai_review 等实际处理中状态，明确完成条件，兼容升级 CLI 调用方。

## 必需验证

使用假时钟和模拟 RPC 验证退避边界、重复确认、并发 pump、崩溃恢复、接管与迟到回执竞态、心跳过期、旧任务兼容、逐项遗漏、重启后的事件去重，以及等待超时保持真实状态。每项须具备 CLI/API 和界面一致性证据，不操作真实绑定或投递真实测试任务。
